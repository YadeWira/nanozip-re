# Quirks, defects and loose ends of the original `nz` 0.09 alpha

NanoZip never had a stable release: 0.09 alpha (2011) is the last build Sami Runsas
published, and it still carries the rough edges of an alpha. This page collects the ones
measured while making nanozip-re behave like the original — every item below was observed on
`nz 0.09 alpha/Linux32` (and, where noted, on the Windows build), not inferred from the
decompile. It is meant as a reference for anyone writing a compatible tool: some of these
must be *reproduced* to stay compatible, others are best left behind.

**Policy (2026-09-03):** nanozip-re reproduces the original first, defects included, so that the two
binaries can be compared on equal terms; which of these defects to keep and which to fix is a decision
for the community once the decoder is complete, and it will be taken with this list in hand. Until
then the only escape hatches are environment variables (`NZ_SAFE=1`, `NZ_STRICT_EXIT=1`), never new
switches. The verdict column says what nanozip-re does today.

| # | Area | What the original does | nanozip-re |
|---|------|------------------------|------------|
| 1 | exit status | **Always 0**, on every path: unknown command, missing archive, foreign file, corrupt data, checksum mismatch. Scripts cannot tell success from failure. | Reproduced. `NZ_SAFE=1` or `NZ_STRICT_EXIT=1` return 2 for damaged or undecodable content (`NZ_STRICT_EXIT` also gives distinct codes for usage errors). Pending the community's decision. |
| 2 | damaged archives | Writes whatever it decoded. Output is flushed per codec block (`-co`/`-cO`/`-cc`: the block is a whole type group up to the window, so a 6 MB text file yields nothing; `-cc` blocks of ~2 MB flush individually), per 1 MB stream for `-cd`/`-cD`, per member for `-cf`/`-cF`. When a block fails: the files of the blocks before it are on disk, the file the failing block starts with is **created empty** (a file it cut mid-way keeps the bytes of the earlier blocks), nothing is warned per file — only `Archive corrupted. Error decoding (code N)`. When decoding completes but a checksum fails: the wrong file is written, `Checksum mismatch [stored computed]: file` is printed and the footer follows. | Reproduced: 42 of 48 corruptions leave the same tree and 39 of 48 print the same report (see 4); the rest are decoder garbage on corrupt audio and lzpf blocks, the crashes of 27 and the store truncation of 26 |
| 3 | overwrite prompt | `Overwrite <file> (Yes/No/Always)?` reads a raw key. When stdin is not a terminal (pipe, `/dev/null`, a script) the read fails and the prompt is **re-printed forever**, at full speed — 1.7 GB of prompt text per minute in our test, until the disk fills. `-y` avoids it. | Reads a line; end of input counts as *No*. [pending] |
| 4 | error codes | `Archive corrupted. Error decoding (code N)` carries one STATUS per codec, printed **plain** when a later record made the driver notice it and as **N·256 + stream slot** when the failing record was the archive's last or the input ended (so a truncated archive says 25600, 4096, 1536, 512 …). Statuses: `-co`/`-cO`/`-cc` 100 payload check, 101 LZ output, 102 buckets, 103 inverse BWT, 104/105 param14/15, 107/108 param2/1, 109 text, 110/111 final/dece (per-stage check bytes, see 25), 2 image block, 16 audio block, 3 bucket decode, 5/7 param14/15 failing, 12 text pipeline failing, 14 output over capacity; `-cd`/`-cD` 2 CM chunk, 3 prefilter chunk, 5 token loop, 6 text pipeline, 10/11/13 output beyond total, 16 chunk header past the stream; `-cf`/`-cF` 2 header beyond input, 3 out_size over the remaining output, 4 out_size ≥ 0x8001, 5 sub-decoder, 6 block consuming more input than the stream holds, 7 output over the window; store 1. A clean-but-short `-cd` decode says `Archive corrupted. Unexpected end of file.` instead. Measured with GDB on the report method (`FUN_0804ae80`) and the codec objects' status methods (`FUN_0809c8c0`, `FUN_080aa850`, `FUN_08097e20`, `FUN_080913e0`). | Reproduced: the same channel, codes and plain/·256 rule (39 of 48 damaged cases print the identical line; the rest are the crashes of 27, the uninitialised memory of 26 and four `-cf`/`-cF` cases where the original decodes a corrupt block's garbage differently). |
| 5 | archive name | `.nz` is appended unless the name already ends in `.nz` or `.exe`, **case-sensitively**: `m.NZ` becomes `m.NZ.nz`, `m.EXE` becomes `m.EXE.nz`. `-nofilenameext` disables it. | Reproduced. |
| 6 | foreign files | A file that is not an archive is probed by reading record headers; when the first record type happens to be 14 the *next* byte is reported as a version number: `Archive file is made with incompatible version (1.12)` for a text file starting with `Nano…`, `(0.97)` for the four bytes `Nano`. Random data usually gets `File is not a NanoZip archive.`, but not always. | Reproduced (the probe is ported), since the message text is part of the interface. |
| 7 | `-` switch | Documented in the usage text as "stop scanning switches", but on `l`/`t`/`x` a lone `-` is rejected: `Unknown argument: -`. | Reproduced. |
| 8 | switch values | Values must be attached: `-o out` makes `out` the archive name (so `Archive: out.nz` / `Cannot open archive!`), `-x` alone is `Unknown argument: -x`. `-m` accepts decimals (`-m1.5g`) but `-mfoo` is rejected; `-p`, `-m`, `-o`, `-t`, `-br`, `-bw` may be empty and are then ignored. | Reproduced. |
| 9 | switches anywhere | Switches are recognised in any position after the command: `x archive -y` overwrites, `x archive -v` shows the verbose header. A file argument beginning with `-` therefore cannot be given. | Reproduced. |
| 10 | `l` ignores file arguments | `l archive some/file` lists the whole archive; the arguments are silently dropped. | Reproduced. |
| 11 | `-swapinout` / `-forceout` | Benchmark helpers with odd corner cases: with no file argument `-swapinout` makes the archive name `*` (`Archive: *.nz`), and `-forceout` writes every extracted entry to a file literally named `*`. | Reproduced. |
| 12 | `-t<n>` on decode | Caps the reported `Threads:` value; `-t0` and values above the CPU count mean "auto". It does not appear to change the decode itself. | Reproduced (and it also caps the decoder's own thread pool). |
| 13 | `Compressor #k` order | On a multi-threaded (`-pN`) archive the per-worker lines come out in **thread-scheduling order**, different from one run to the next, interleaved with the progress redraws. | Deterministic stream order (0..N-1). Only difference left on those archives. |
| 14 | container record order | The metadata records of the worker streams are likewise written in the order the threads finished, not stream order: a decoder that assumes stream 0 comes first mis-parses about one archive in twenty. | Handled (was a bug here once). |
| 15 | progress line | Redrawn from a ~0.5 s timer, only when the megabyte figure or the current file changed; the figure is *cumulative* over the whole archive, rounded (`0 MB` … `3 MB`); names over 40 columns are shown as `...` plus their last 37 characters; the name/figure/backspace choreography is fixed. The number of redraws therefore varies between two runs of the same command. | Same rules; the redraw count still differs by timing. |
| 16 | `IO-out` in the footer | `IO-in: 0.00s, 51 MB/s. IO-out: 0.00s, 738 MB/s` appears only when the write phase happened to take measurable time; on a fast machine the same archive shows it in one run and not the next. | Not reproduced (timing-dependent). |
| 17 | `[N MB]` figure | The compressor line's memory figure is the codec's own memory-usage method, which mixes window size, table sizes and fixed allocations (e.g. `nz_cm [419 MB]` at the default `-m512m`, `nz_lzpf_large [68 MB]` even for a 20-byte input); it says nothing about what the *decoder* will use. | Reproduced to the byte (transcribed formulas). |
| 18 | `-v` on decode | Adds only ` IO-buffers: 0+1 MB.` (`t`) / ` IO-buffers: 0+4 MB.` (`x`) to the compressor line and exact byte counts to `l`; nothing else is more verbose. | Reproduced. |
| 19 | listing units | The `size` column steps up to the next unit once the value exceeds *nine* of the current one (9216 B prints as bytes, 9300 as `9 KB`; exactly 9 MB prints as `9216 KB`) and rounds rather than truncates. | Reproduced. |
| 20 | self-extractors | `l`/`x`/`t` accept a `.exe` made with `w32c`: the opener parses the PE header and seeks past the image. A PE whose section table it cannot read yields `File is not a NanoZip archive.`. | Reproduced (PE offset ported). |
| 21 | checksum coverage | With `-pN` (the default above ~8 MB) a file that spans several worker streams has **no whole-file checksum** — each stream checksums only its slice, and `l` shows `n/a`. | Same; slices are verified individually. |
| 22 | `decr_param 3` | The block type the image model uses (uncompressed BMP/PGM/PPM/TGA/TIFF) is decoded by the original; the community reference decoder (`nzdec_v0`) treats it as ordinary CM and fails every such file — a documentation gap of the format, not a defect of `nz`, but the source of most third-party decoding failures. | Ported. |
| 23 | 32-bit memory | The 32-bit Linux build decodes multi-gigabyte archives fine (it streams); it prints `Out of memory!` when the *compressor's* model does not fit. | Our 32-bit builds hold the decoded stream in memory and print `Out of memory!` on archives whose content does not fit; use the 64-bit build for those. |
| 24 | `a` on the current directory | `a archive.nz` with no file arguments quietly archives whatever is in the current directory (in our test: the shell's own redirect target). | Not applicable (encode not implemented; an error is printed). |
| 25 | per-stage check bytes | Every `-co`/`-cO`/`-cc` block header carries one check byte per decoding stage (payload, entropy-decoded BWT buckets, inverse BWT or LZ/CM output, param14, param15, param2, param1, the text-transform chain): the archive's Fletcher-32 of that stage's buffer **modulo 255**, stored in stage order and consumed from the end (`FUN_080c0220` pops the last byte after each stage). A mismatch stops the block before anything is written: `code 100`, or 103 on the last stage of a BWT block. The community reference decoder skips these bytes ("staged_checksum_count"). Found with a GDB read-watchpoint on the byte. | Reproduced (one byte in 255 escapes both). |
| 26 | truncated store archive | `-cn` archive cut at 85 %: all five files are created at **full size**, the cut one and every later one filled with garbage, four `Checksum mismatch` lines (three computed as `ffffffff`), exit 0. | `Data corrupted while reading headers!`, nothing written. Not worth reproducing. |
| 27 | crashes on damaged archives | Corrupt input can kill the original: a `-cD` corruption aborts with `*** glibc detected *** free(): invalid pointer` (exit 134) after printing `Error decoding (code 6)`; another `-cD` and one `-cF` corruption **segfault** (exit 139) with no message; the outcome depends on the memory layout (under GDB with ASLR off the segfaulting `-cD` case prints `code 4096` instead). A multi-file `-cd -p4` container cut at 85 % also segfaults (exit 139), after creating some of its files. | Not reproduced: nanozip-re prints the code the original would have reached (fuzzed 1358/1358 clean). |
| 28 | archive of only empty files | `x` on an archive whose files are all zero bytes **segfaults** (exit 139) and writes nothing; an archive mixing empty and normal files extracts fine, empty files included. | Not reproduced: the empty files are created. `[pending]` |
| 29 | path traversal | An entry named `../../../x` is written **outside the extraction directory**; an absolute `/tmp/x` is written as `tmp/x` under it (leading slash dropped). No warning. | Not reproduced: the entry is skipped with `Skipping unsafe path in archive:` on stderr and counted in the footer. `[pending]` |
| 30 | directories | Every directory created on extraction has mode **0700**, whatever the umask. `a` takes file *patterns*, not directories (`a x.nz dir` is `No files found with dir`; `-r 'dir/*'` recurses), and empty directories are never stored. | Reproduced (0700). |
| 31 | timestamps | A file's mtime is stored as epoch **minus** the writer's UTC offset and read back as stored **plus** the reader's current offset, so it is only right in the writer's time zone (2·offset skew elsewhere: a 12:34 -0500 file lists as 22:34 under UTC). All of it in 32-bit `time_t`: a 2038 or 2100 mtime lists and restores as 1901 or 1963. A timestamp that comes out as exactly 0 prints as an **empty** date column and is not applied; negative ones (1969) print and apply normally. | Reproduced (skew, wrap, empty field). |
| 32 | write failures | A file that cannot be created (read-only directory, a directory in its place, `-o` naming a file or `/`) prints `Cannot write: <path>` on its own line and the run continues to the normal footer, exit 0. | Reproduced. |
| 33 | `-forcemem`, `-continue`, `-pause` | `-forcemem` is accepted with `Warning: Ignoring deprecated option -forcemem.` as the first line; `-continue` is accepted silently (undocumented); `-pause` prints `Press enter to continue...` (no newline) after the footer and reads a line. | Reproduced. |
| 34 | `Unknown command` | Two formats: `Unknown command q` for a one-character token, `Unknown command: qq` for two or more characters — and for the empty token (`nz "" archive`). | Reproduced. |
| 35 | `-fo` | With `-fo` the listing gains a `user/grp.` column (`%4u/%4u`) after the mode, only when the archive was made with `-fo` (record types 8 and 9, u16 runs); on other archives the switch changes nothing. | Reproduced (listing); ownership is not restored (needs root). |
| 36 | `l` name width | The plain listing shortens names over 40 columns to `...` plus the last 37 characters, like the progress line; `l -v` prints them whole. | Reproduced. |
| 37 | `s` and `w32c` | `s` (simulate) with a non-existent first file prints `No files found with <name>` and then simulates on the remaining arguments into `<dummy>.nz`; `w32c archive.nz` asks `Overwrite archive.nz (Yes/No/Always)?` about its own input and, with stdin not a terminal, loops forever (see 3). | Not applicable (encode / SFX creation not implemented; `w32c` prints a refusal). |
| 38 | image detectors | The image model is engaged for 24-bit BMP, 24-bit TGA, binary PGM (8- and 16-bit) and PPM; 8/16/32-bit BMP, 32-bit TGA, PBM and uncompressed TIFF are compressed as ordinary data. Its predictor always runs in mode 2 (`(left+above+1)>>1`): none of the other seven modes the decoder implements has ever been emitted (synthetic gradients and 240 real images). | Reproduced (all decode byte-exact); modes 0/1/3-7 stay ported-but-unexercised. |
| 39 | `Internal error` | Failed assertions inside the engines print `Internal error: <id>! Please report this to sami (at) nanozip.net.` (after a newline, the status line is not cleared) and exit **255**, the one status not laundered to 0 (see 1). The ids are constants of the code: 21231532 is nz_lzhds' reconstruct finding a match longer than the chunk (a corrupt or truncated `-cD` stream), 9256352 an unknown codec byte, 100 is `Out of memory!`; 22563525 appears from a thread-teardown race on some truncated `-cd` archives (one run in three). | Reproduced for 21231532 (same line, exit 255); the race is not. |
| 40 | `-cO` LZP table wrap | When the ring scrolls, the LZP hash table is cleared except its **last 16 entries** (hashes 0xfff0–0xffff), which keep stale positions; a later hit on them resolves against the new ring contents. | Reproduced (`nz_optimum2_lz.cpp`, the wrap sweep). |
| 41 | parallel containers on damage | A `-pN` container is written by its **workers**, each straight into the output files at absolute offsets (one `open` per worker on the same file). A worker whose stream fails leaves a **hole of zeros** the size of its slice (the file keeps its full length when a later slot wrote past it; it ends short when the failing slot was the last). The CM family flushes per codec block (a failing slot keeps its completed blocks), lzpf per member segment and `-cd`/`-cD` per file group: nothing of the unit in flight survives a status error, but a stream that merely ends short flushes what it produced. A group's first file is created, empty, when the worker starts the group; later files when bytes reach them; groups after a failure never appear. The other workers **carry on**, so a damaged 16-stream archive still writes 15 good slices. Slice checksums are verified as each slice completes and a mismatch prints `Checksum mismatch [stored computed]: <file>` (the slice's values under the file's name), then the normal footer, exit 0; a status error prints `Archive corrupted. Error decoding (code status·256 + slot)` and no footer. A data record cut by the end of the archive is dropped (the compressed workers never see it; a `-cn` worker copies its bytes and zero-pads the slice), and the cut worker reports a codec-specific short-end status: `-cc`/`-co` `Unexpected end of file`, `-cO` 100, lzpf 2 (4 when a whole group had no data left), `-cd`/`-cD` 4 (1). | Reproduced (the sink in `sfx_archive.cpp`, `namespace psink`; measured on 8 codecs × 7 corruptions × single- and multi-file: files identical in 100+/112, see README). |
| 42 | lzpf worker overruns | Inside a parallel stream the lzpf worker does not stop when a block's side data runs past its record or its output would overshoot the slice: it clamps, produces garbage and reports at the **next** block header (`code 4` or `2`), where the single-stream decoder reports the overrun itself (`6`, `3`). | Reproduced (`DecodeLzpfMember` lenient mode for parallel streams). |

## Things that are *not* defects but surprise people

- **Compression is not reproducible byte-for-byte across thread counts**: the same input
  compressed with `-p1` and with the default gives different archives (different stream
  splits). Decoding either is fine.
- **The window size is a byte, not a number**: `bytefloat(p1 + 1)` in 64 KB units (a 4-bit
  mantissa and exponent) is what every codec derives its window/dictionary/ring from, so
  the actual window is rarely exactly what `-m` asked for.
- **The version string is a record**: an archive begins with a type-14 record holding
  `NanoZip 0.09 alpha` and a type-30 record holding the byte 9; the "incompatible version"
  message reports that byte divided by 100.

## How these were measured

Two harnesses drive the original and nanozip-re through identical invocations and compare
stdout, stderr, exit status and the tree of written files (mode, timestamp, size, path):
`matrix.sh` (36 command/format cases) and `matrix2.sh` (78 switch cases), plus
`corrupt_compare_all.sh` (one flipped byte at five offsets and a truncation, on a five-file archive
of every codec, 48 cases; `x`, `l` and `t`, trees and report lines compared), and `matrix3.sh` (77 cases on hand-built trees: empty files, links,
odd names, modes, extreme mtimes, hostile paths, `-o`/`-x`/`-sp` corners, time zones and
locales). They live with the project's private tooling and are described in the wiki's
Reverse-Engineering-Notes.
